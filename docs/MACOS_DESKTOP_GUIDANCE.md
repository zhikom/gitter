# macOS desktop integration guidance

Research checked 14 November 2026 against Apple and Tauri documentation and the local Gitter source. Recommendations below are design choices for Gitter; they are not claims that the current app already behaves this way. This is a source review, not a runtime or accessibility audit.

**Implementation update:** Gitter now has a native macOS app menu with About,
Settings, and Check for Updates, plus File, Edit, Repository, View, Window,
and Help menus. Its window title follows the active repository and branch, and
an explicit update check fetches a fresh result. The Settings action currently
opens Gitter's existing modal, not a separate native settings window; restoring
the last settings pane and signed/notarized automatic updates remain follow-on
work. The observations below describe the source baseline before these changes;
they are retained to explain the decisions and verification still needed.

## App menu, settings, and About

- Apple places app-wide commands in the App menu. Its typical order is **About Gitter**, a separator, **Settings…**, other app-level configuration commands, Services, Hide Gitter, Hide Others, Show All, and Quit Gitter, with separators between logical groups. About should be first and contain version and copyright information. Apple advises preserving standard shortcuts and making app commands available from the menu bar. [Apple: The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- Apple says **Settings…** belongs in the App menu and opens a settings window; Command-comma is the expected shortcut. A dedicated settings window should restore the last pane and reflect the selected pane in its title. App settings belong there; document-specific settings belong in the File menu. The current [Settings modal](../src/components/Modals/SettingsModal.tsx) combines global and repository-specific sections, so a future split or separate repository entry would be closer to this guidance; a modal can be reused initially as a pragmatic step. [Apple: Settings](https://developer.apple.com/design/human-interface-guidelines/settings)
- **Recommendation:** put **Check for Updates…** after Settings in the app-level group, reusing the existing update action. Apple shows a Check for Updates action in its menu customization example, while the placement here follows its grouping advice; the specific placement is a recommendation. [Apple: Building and customizing the menu bar](https://developer.apple.com/documentation/swiftui/building-and-customizing-the-menu-bar-with-swiftui), [Apple: The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- Gitter already defines `settings` (`Mod+,`) and `check-updates` commands in [App.tsx](../src/App.tsx), and the Settings About section exposes the version and update action. Its [shortcut handler](../src/commands.ts) supports user overrides and suppresses shortcuts while a dialog is open. Route native items through the same actions and decide how standard Command-comma and user overrides interact; test a keypress invokes the action once and that an open modal does not get unexpectedly replaced. App-wide commands should be useful on the welcome screen too.
- Tauri's [native About item](https://docs.rs/tauri/latest/tauri/menu/struct.PredefinedMenuItem.html) and [AboutMetadata](https://docs.rs/tauri/latest/tauri/menu/struct.AboutMetadata.html) can supply name, version, and copyright. Its documentation marks authors, comments, license, website, and website label unsupported on macOS; do not assume those fields become clickable About content there. The default Tauri menu supplies package name and version, but Gitter's [bundle configuration](../src-tauri/tauri.conf.json) currently has no explicit copyright field; verify the actual About panel contents and supply accurate metadata if desired. A richer Gitter About view remains an option when links or diagnostics are required. [Tauri default menu source](https://docs.rs/tauri/2.12.5/src/tauri/menu/menu.rs.html)

## Native Tauri menu integration

- The [current Rust setup](../src-tauri/src/lib.rs) does not create a custom menu. Tauri 2.12.5 enables the default macOS menu; its source shows About, Services, Hide, Hide Others, and Quit, as well as default File, Edit, View, Window, and Help menus. Settings, update checking, and Show All are not in its default App submenu. Preserve the useful system actions when customizing it. [Tauri Builder](https://docs.rs/tauri/latest/tauri/struct.Builder.html#method.enable_macos_default_menu), [Tauri 2.12.5 default menu source](https://docs.rs/tauri/2.12.5/src/tauri/menu/menu.rs.html)
- On macOS the menu is application-wide, not per-window: attach it via `AppHandle::set_menu`, `Menu::set_as_app_menu`, or the builder's app menu API. All top-level entries must be submenus; Tauri says the **first submenu becomes the App menu**. Prefer native predefined items for standard About, Services, visibility, Quit, Edit, and Window actions; use stable custom item IDs for Gitter actions. [Tauri window menu guide](https://v2.tauri.app/learn/window-menu/), [Tauri Window menu behavior](https://docs.rs/tauri/latest/tauri/window/struct.Window.html#method.set_menu), [Tauri predefined items](https://docs.rs/tauri/latest/tauri/menu/struct.PredefinedMenuItem.html)
- Handle custom menu events by ID, dispatching into the current frontend command state. If the menu is created in Rust, Tauri supports emitting an event to the relevant webview; avoid stale closures, unregister listeners on cleanup, and account for the period before the webview is ready. Gitter creates the main window only after backend startup. Alternatively, Tauri provides JavaScript menu APIs and callbacks; manage the lifetime of their resources when rebuilding menus. Gitter's existing `core:default` includes the default menu and event permissions, but check the exact permissions for the chosen API. [Tauri menu guide](https://v2.tauri.app/learn/window-menu/), [Tauri frontend events](https://v2.tauri.app/develop/calling-frontend/), [Tauri core permissions](https://v2.tauri.app/reference/acl/core-permissions/), [Gitter window config](../src-tauri/tauri.conf.json)
- **Recommendation:** keep macOS changes scoped to macOS and preserve Windows menu behavior. If adding broader menus, mirror relevant Gitter commands under File, Edit, View, Repository, Window, and Help; disable unavailable commands and keep labels and shortcuts in sync with actual state. Apple recommends a Window menu with Minimize and Zoom even for one window and using a View menu for visibility and full-screen controls. [Apple: The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar), [Apple: Menus](https://developer.apple.com/design/human-interface-guidelines/menus)

## Dynamic window title and repository context

- Apple recommends concise, useful window titles that identify content and distinguish windows; an app name alone does not provide that context. [Apple: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)
- **Recommendation:** use the active repository's name for the main window title, optionally with the branch when it adds useful context; use a neutral welcome title when no repository is active. Distinguish duplicate repository names using a short parent path if needed. On tab switching, closing the last tab, failed repository loading, branch changes, and worktree changes, update or clear the title so it never identifies a previously active repository. The current [window config](../src-tauri/tauri.conf.json) sets `Gitter`; [App.tsx](../src/App.tsx) already holds the active path and current repository state.
- **Recommendation:** keep the title short; provide the full local path through an accessible tooltip, copy action, or Reveal in Finder, and show branch, detached HEAD, staged/unstaged/untracked counts, conflicts, and merge/rebase state in the repository UI when useful. The [repository state](../shared/types/git.ts) already carries those fields, and the [tab bar](../src/components/Navigation/RepoTabBar.tsx) already exposes path, branch, and an uncommitted-changes indicator. Avoid including remote credentials or lengthy paths in a title visible in screenshots or window switching.
- Tauri exposes Rust `set_title` and JavaScript `getCurrentWindow().setTitle(...)`. The JS call requires `core:window:allow-set-title`, which is **not** in `core:window:default`; the current [capability](../src-tauri/capabilities/default.json) grants only `core:default` and dialog open. Guard frontend-only calls for the browser build and handle failed or out-of-order async updates. [Tauri Window API](https://v2.tauri.app/reference/javascript/api/namespacewindow/#settitle), [Tauri capabilities](https://v2.tauri.app/security/capabilities/), [Tauri Rust Window API](https://docs.rs/tauri/2.12.5/tauri/window/struct.Window.html#method.set_title)
- AppKit's `representedURL` can associate a file URL with a window, enabling a title-bar icon and a Command-click path menu for an existing file. Tauri exposes a native `NSWindow` through its platform API, but this is additional macOS-specific interop and its usefulness for a **directory representing one active tab** has not been verified. If explored, update or clear the represented URL on tab changes and test real directory behavior; `setTitle` alone does not provide these document semantics. [Apple: representedURL](https://developer.apple.com/documentation/appkit/nswindow/representedurl), [Tauri WebviewWindow](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindow.html#method.with_webview)
- Do not equate a dirty Git working tree with an unsaved document. AppKit's document-edited state describes changes that need saving; Gitter's uncommitted files are a different concept. Keep that indicator in repository UI unless Gitter introduces an actual unsaved document. [Apple: documentEdited](https://developer.apple.com/documentation/appkit/nswindow/isdocumentedited)

## Update-check behavior to verify

- The current startup check is cached in [App.tsx](../src/App.tsx), and [UpdateModal](../src/components/Modals/UpdateModal.tsx) only checks on opening if it receives no initial result. **Recommendation:** an explicit Check for Updates action should run a fresh check, show progress and errors, and distinguish an up-to-date result from a network failure; keep background checks unobtrusive.
- On macOS, [appUpdate.ts](../server/appUpdate.ts) selects a DMG, and [osIntegration.ts](../server/osIntegration.ts) opens it with the system `open` command. The existing dialog says an installer is running and that Gitter will close and restart. Opening a disk image alone does not verify application replacement or restart; verify the actual end-to-end flow and use wording that describes the action performed until automatic installation exists. The current release handler checks that the requested asset belongs to the latest GitHub release; the inspected download path does not perform a separate artifact-signature verification.
- Tauri's optional [updater plugin](https://v2.tauri.app/plugin/updater/) is a separate implementation path that requires signed update artifacts and signature verification. Adopting it would require its own release and key-management work; it is not necessary merely to add the menu command. Apple code signing and notarization are separate distribution concerns and should not be implied by an ad-hoc signature.

## Suggested manual verification

On macOS, inspect menu ordering and About metadata, then exercise Settings and Check for Updates from the welcome screen and a repository, with a modal open and with a shortcut override. Test Command-comma once per press, normal Edit shortcuts in text fields, Hide/Show/Quit, and Window actions. Switch repositories and branches, close the last tab, and exercise an unavailable repository; verify title, context, and stale-state handling. Check online, offline, up-to-date, and new-release update flows, including what actually happens after opening the DMG. Repeat startup/early menu interaction and confirm the browser and Windows paths still work. These are proposed checks, not results from this research.
